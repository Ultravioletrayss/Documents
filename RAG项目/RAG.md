# 一句话先讲明白

👉 **Embedding 是“把文本变成向量”**
👉 **向量库 是“存这些向量并支持搜索”**

可以理解成：

```text
文本 →（Embedding模型）→ 向量 →（向量库）→ 存储 + 检索
```

---

# 一、Embedding 到底是什么？

本质是一个函数：

```text
text → vector（高维向量，比如768维 / 1536维）
```

比如：

```text
“公司盈利能力很好” → [0.12, -0.87, 0.33, ...]
```

### 它做了什么？

👉 把“语义”变成“数学空间里的位置”

也就是说：

* 语义相似 → 向量距离近
* 语义不同 → 距离远

例如：

```text
“净利润增长” ≈ “盈利提升”
```

👉 向量会很接近

---

# 二、向量库是什么？

你可以把它理解成一个**“专门存向量 + 支持相似度搜索的数据库”**

常见的：

* FAISS（本地高性能）
* Chroma（轻量级）
* Annoy（低内存）

---

## 向量库存什么？

每一条数据一般是：

```text
{
  vector: [0.12, -0.87, ...],
  text: "原始财报内容",
  metadata: {
    公司: "贵州茅台",
    年份: 2023,
    页码: 45
  }
}
```

👉 所以你说得对：
✔ 向量库“是存储”
❗但不仅仅是存储，还负责**检索**

# 报错处理或者识别异常处理：
以下是**面试版本**的补充报告（口语化、自然版），你可以直接拿来用，或者稍作调整。语气像你在真实面试中跟面试官聊天一样，逻辑清晰、不生硬。

---

**面试官追问补充：提取 + 多维度验证 + 置信度 gating + 来源追溯**

面试官如果问：“财报里表格特别容易识别错，你是怎么保证数据准确性的？”  
你可以这样接：

“对，这个问题很关键。因为财报里利润表、资产负债表、现金流量表这些表格，经常有无边框、合并单元格、跨页的情况，单纯靠一个工具很容易出问题。我在项目里没有指望‘一次抽取就完美’，而是做了一整套‘提取 + 多层把关 + 置信度控制 + 来源追溯’的组合，确保错误尽量在早期就被拦住。”

**具体是怎么做的，我分四步说：**

**第一步：提取阶段用混合工具，避免单一工具的短板**

我没有只用 pdfplumber 或者只用 Camelot，而是把两个工具结合起来：

- 先用 **pdfplumber** 扫整个页面。它对文字提取和页面布局理解很强，能拿到精确的字符位置、线条信息，还能初步发现表格在哪。
- 然后针对检测到的表格区域，再用 **Camelot** 做专项提取：
  - 如果页面有明显边框线，就用 Camelot 的 Lattice 模式（它对有网格的表格特别准）。
  - 如果是财报里最常见的无边框、靠空格对齐的表格，就用 Stream 模式。

这样做的好处是：pdfplumber 提供细粒度的布局控制，Camelot 负责专业的表格结构识别。实际测试A股年报时，这种混合方式比只用 pdfplumber 的 extract_table() 要稳不少，尤其是处理那些隐形表格的时候。

**第二步：多维度验证，把明显错误卡在预处理阶段**

抽出来之后，我不会直接把表格扔进向量库，而是先做几层验证：

- **会计等式交叉验证**（这是最硬核的一层）：  
  资产负债表必须满足 **资产 = 负债 + 所有者权益**，允许很小的四舍五入误差。如果不等，我就标记这个表格有问题。
  
- **内部一致性检查**：合计行是否等于下面所有子项之和？本期期末数是否等于下期期初数？单位是否统一（都是万元还是元）？

- **合理性规则检查**：毛利率是不是在正常区间？负债率有没有异常高？结合这家公司历史数据简单比一下。

如果哪一步没通过，我就知道这个表格大概率抽取有问题，不会盲目信任它。

**第三步：给每个表格打置信度分（Confidence Gating）**

我给每个提取出来的表格或关键指标打一个 **0-1 的置信度分数**，计算方式大概是：

- Camelot 自带的 parsing_report（accuracy 和 whitespace）占一部分权重
- 会计等式和一致性验证是否通过占一部分
- 数值合理性再占一部分

分数高（比如 0.85 以上）的，就正常进入后续流程；  
分数低的，就标记为“低置信数据”，在给 LLM 的上下文里会特别注明，同时在前端输出时也会告诉用户“这部分数据建议人工再核对一下原 PDF”。

这样做的目的是：不让低质量数据偷偷溜进最终答案，强迫系统更保守。

**第四步：全程来源追溯（Traceability）**

不管是哪一步出的结果，我都会把原始出处记录下来，包括：
- PDF 文件名、公司名、年份
- 具体页码
- 是哪个 section（比如“合并利润表”还是“附注”）
- 甚至表格在页面上的坐标

用户看到答案时，如果点某个数字或句子，能直接跳转到原 PDF 的对应页面。这样即使万一有错，用户也能快速定位去查原始文件，符合投研场景里“可审计”的要求。



### **一、原始流程（我最早做的版本）**

最早我做的其实就是一个比较标准的 **Naive RAG** 流程，适合快速验证想法，但放到财报上问题比较明显：

1. **数据输入**：拿到上市公司PDF财报（年报/季报）。
2. **预处理**：用 PDF 解析工具（主要是 pdfplumber）把整本报告转成文本，然后按固定长度（比如 800 tokens）粗暴切成很多小块（chunk）。
3. **向量化**：把每个 chunk 用 embedding 模型转成向量，存进向量数据库（比如 Chroma 或 FAISS），同时记录一些基本 metadata（公司名、年份、页码）。
4. **用户提问**：用户问问题 → 把问题也转成向量。
5. **检索**：在向量库里找最相似的 top-k 个 chunk。
6. **生成**：把检索到的 chunk 塞进 Prompt，给 LLM 生成答案。
7. **输出**：直接把答案展示给用户。

**这个原始流程的问题**（面试官问到时你可以主动说）：
- 表格经常抽取错位、合并单元格丢了、数字对不上。
- 没有专门验证，LLM 拿到错误数据就容易给出错的分析。
- 问具体数字（如“2023年净利润多少”）时，经常不准或幻觉。
- 没法很好处理跨年对比。
- 来源不清晰，用户不知道答案来自哪一页。

整体就是“拿来主义”：PDF → 简单切块 → 向量检索 → LLM，速度快但准确度不高，尤其不适合金融这种对数字要求严格的场景。

### **二、加上补充流程后的总体流程（现在优化版）**

现在我加了“**提取 + 多维度验证 + 置信度 gating + 来源追溯**”这套机制后，整个 pipeline 变得更严谨、更适合财报分析了。核心思路是：**不在后期靠 LLM 纠错，而是在前期就把错误尽量堵住**。

下面是完整的优化后流程（你可以边说边简单画出来）：

**1. 数据输入层（不变）**  
拿到 PDF 财报（利润表、资产负债表、现金流量表、MD&A 等）。

**2. 预处理 & 提取层（这里改动最大）**  
- 先用 **pdfplumber** 做页面级扫描：提取文字、检测线条、获取精确布局信息，同时初步发现表格位置。
- 再针对表格区域，用 **Camelot** 专项提取：
  - 有明显边框 → Lattice 模式
  - 无边框（财报最常见）→ Stream 模式
- 文本部分正常转成 chunk，表格单独转为 Markdown 或结构化格式。
- **新增**：把关键财务指标额外抽取出来，存到 PostgreSQL（结构化数据库）里，方便后面精确查询。

**3. 多维度验证层（新增的核心防错关卡）**  
抽取完后，立刻做几层检查：
- 会计等式验证（资产 = 负债 + 所有者权益？合计行对不对？本期末 = 下期初？）
- 数值合理性检查（毛利率、负债率等是否在正常范围）
- 内部一致性检查（子项加起来是否等于合计）
- 如果验证不通过，就标记为可疑。

**4. 置信度打分 & Gating（新增）**  
给每个表格和关键指标打一个 **0~1 的置信度分数**（综合 parsing accuracy、验证通过情况、合理性等）。
- 分数高（≥0.85）→ 正常进入向量库和结构化库。
- 分数低 → 标记“低置信”，在给 LLM 时会特别提醒，同时前端会告诉用户“建议核对原 PDF”。

**5. 向量化 & 存储层**  
- 文本 chunk + 处理后的表格（Markdown）→ embedding → 向量数据库。
- 同时保留丰富 metadata（公司、年份、页码、section、表格类型、置信度）。
- 关键指标还额外存结构化数据库（支持 SQL 精确查）。

**6. 用户提问 & Query 处理**  
用户问题 → 意图识别（是问具体数字？趋势？还是定性分析？）→ 生成多个子查询（RAG-Fusion）。

**7. 检索层（优化后）**  
- 先用 metadata 过滤（比如只看某年或某张表）。
- 再做 hybrid 检索（向量 + 关键词）。
- 对于精确数字问题，**优先走结构化数据库（SQL）**，向量检索只做补充。
- 检索结果经过 reranker 重新排序。

**8. Prompt 构建 & LLM 生成**  
- 把高置信度的上下文 + 来源 + 置信度分数 一起喂给 LLM。
- 系统 Prompt 强调：只能基于提供内容回答，数值必须带来源，低置信要标注。
- 对于需要计算的部分，额外用代码解释器精确算，避免 LLM 算错。

**9. 输出层**  
- 答案 + 关键数据高亮 + 来源链接（点一下跳到 PDF 原页）。
- 低置信内容会明确提醒用户。

---

**总结对比（面试收尾很好用）**：

原始流程就像“快速扫描一遍财报就回答”，速度快但容易出错。  
优化后流程相当于“先仔细检查表格和数字有没有问题，再决定信多少、怎么用”，准确度明显提升，特别适合金融投研场景对数据可靠性的要求。

虽然不能做到 100% 零错误（PDF 格式太复杂），但通过多层验证 + 置信度控制 + 来源追溯，系统会更保守、更可信，用户也知道什么时候该自己再看原文件。
